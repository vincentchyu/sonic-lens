# WeChat 文章生成约束

这份文件定义 SonicLens 公众号文章的生成、引用和归档规则。  
目标是保证每次生成都能落到独立文章目录中，同时保留 `output/` 作为稳定兼容入口。

## 目录规范

- 当天生成的公众号文章必须放入独立目录，命名格式为 `sonic-lens_article_YYYYMMDD`。
- 例如 2026 年 4 月 21 日生成的文章目录应为 `sonic-lens_article_20260421`。
- 文章本体资源不得再直接散落到 `output/` 根目录。
- `output/` 只允许保留兼容入口、约束文件和指向文章目录的符号链接。

## 文章资源归属

文章目录内应至少包含以下内容：

- `wechat_article.md`：公众号正文的 Markdown 源文件。
- `wechat_article.html`：公众号可发布的最终 HTML。
- `wechat_article_body*.html`：正文片段，用于组装发布 HTML，允许按迭代保留版本后缀。
- `wechat_article_preview*.html`：带预览壳的本地审核页，允许按迭代保留版本后缀。
- `wechat_article_reader*.html`：读者最终视角版，用于确认最终阅读效果，允许按迭代保留版本后缀。
- `wechat_preview*.html`：本地预览入口页，允许保留兼容页和版本后缀。
- `wechat_assets/`：公众号文章专用素材，例如分享图、长图图块等。
- `wechat_preview_assets*/`：合图后的预览素材，允许按迭代保留版本后缀。

## 引用路径规则

### 1. Markdown 源文件

- `wechat_article.md` 中，引用仓库公共静态资源时使用相对路径 `../static/...`。
- `wechat_article.md` 中，引用文章目录内部资源时使用 `./wechat_assets/...`。
- 禁止把文章正文直接写成 `output/...` 绝对依赖。

### 2. 公众号 HTML

- `wechat_article.html`、`wechat_article_body*.html`、`wechat_article_preview*.html`、`wechat_article_reader*.html` 中，文章目录内部素材统一使用 `wechat_assets/...` 或 `wechat_preview_assets.../...`。
- 不得继续引用旧的 `output/wechat_assets/...` 前缀。
- 若 HTML 需要回退到仓库公共静态资源，应使用可相对解析的 `static/...` 或同层目录引用，避免写死上层输出目录。

### 3. 预览与兼容入口

- `output/wechat_article.md`、`output/wechat_article.html`、`output/wechat_preview*.html` 等文件应当是指向文章目录的符号链接。
- `output/wechat_assets` 与 `output/wechat_preview_assets*` 也应仅作为符号链接存在。
- 预览文件中显示的资源路径必须与文章目录内的真实文件一致。

## 生成流程约束

1. 先在文章目录中生成 Markdown、正文 HTML、预览 HTML 和读者版 HTML。
2. 在生成正文初稿前，先输出一份文章骨架：题目、目标读者、核心观点、每节准备使用的具体事实或例子。
3. 正文写作时必须先完成 `wechat_article.md`，并先做人类可读性自检，再继续生成 HTML。
4. 可读性自检未通过时，不得进入排版、美化和草稿同步阶段。
5. 再把合图素材放入文章目录的 `wechat_assets/` 与 `wechat_preview_assets_v2/`。
6. 最后在 `output/` 中更新兼容符号链接，保持原有打开方式可用。
7. 公众号草稿同步必须在用户确认最终读者版之后再执行。

## 文体与可读性约束

### 1. 总体目标

- 公众号正文必须写成“人能顺着读下去的技术文章”，不是“把项目夸完整”的介绍词。
- 目标文体是“人味正常、能看懂、有判断，但不端着”。
- 优先让读者快速明白“这个项目具体做了什么、为什么这么做、和普通做法有什么差别”。
- 禁止把文章写成简历扩写、功能清单堆砌或 AI 总结腔。

### 2. 句式红线

- 全文禁止高频重复同一种强调句式，尤其是连续使用 `不是……而是……`、`换句话说`、`更重要的是`、`这意味着`、`本质上`、`真正的`、`其实是`。
- `不是……而是……` 及其变体在一篇文章中最多使用 `3` 次；超过即视为明显 AI 味，需要重写。
- 同一段内禁止出现两个及以上“先否定、再拔高”的对照句。
- 能直接正面说清的句子，不要先绕一圈否定别人再表达自己。
- 禁止连续两段都以抽象判断句开头。

### 3. 段落组织规则

- 每一节必须先讲事实，再讲判断；顺序应为“做了什么” -> “为什么这样做” -> “这样做解决了什么问题”。
- 每个三级标题下至少要有一个具体事实支撑，例如模块名、接口名、数据流、失败场景、取舍原因、真实约束。
- 单段尽量只表达一个中心点；一段内如果既讲架构、又讲价值、又讲感受，应拆段。
- 抽象结论后面必须立刻跟一个具体例子，不能只停留在“这是一个闭环”“这是产品化能力”这种判断层。
- 如果一节已经列出事实清单，后续总结段不得只重复“这说明它很完整/很专业/很工程化”，必须补充新的信息或取舍。

### 4. 信息密度规则

- 优先写“读者不知道但值得知道的事实”，减少“作者已经下过结论的评价”。
- 对仓库结构、接口链路、数据模型的描述，应尽量使用项目中的真实名称，例如目录名、表名、接口路径、任务名。
- 空泛评价词如“完整”“专业”“产品化”“工程化”“长期演化”“综合作品”必须少用；每次使用都要有事实锚点。
- 当一段可以改写成更具体的表述时，禁止使用“能力”“闭环”“体系”“价值”这类抽象名词代替细节。

### 5. 人味规则

- 允许保留作者视角，但语气应像开发者复盘，而不是路演文案。
- 可以直接承认麻烦、取舍、脏活和维护成本，这比一味拔高更像真人写作。
- 允许写“为什么我会在意这个细节”，但前提是前面已经把细节本身讲清楚。
- 避免使用过满的自我评价，不要反复证明“这项目很厉害”，而要让事实自己成立。

### 6. 自检清单

生成 `wechat_article.md` 后，必须逐项自检：

- 全文 `不是……而是……` 是否超过 `3` 处。
- 是否有连续三段都在下判断，却没有新事实。
- 是否有某个小节标题成立，但正文只是在重复标题。
- 是否存在“接口很多、能力很多、架构很好”这类空话，删掉后信息量几乎不变。
- 是否能把每个小节各用一句大白话复述给非作者本人听懂；如果不能，说明写得还不够清楚。
- 是否至少保留了 2 到 3 个真实的“为什么这样做而不是那样做”的取舍例子。

### 7. 改写优先级

- 如果文章读起来像在“持续拔高项目意义”，优先删判断句，不优先换形容词。
- 如果文章读起来难懂，优先补具体例子，不优先补总结句。
- 如果文章出现明显 AI 味，优先打散重复句式和段落节奏，不优先做词汇润色。
- 如果一段删掉“这意味着 / 本质上 / 换句话说 / 更重要的是”后意思不变，应直接删除这些连接词。

## 发布前检查

- 检查文章目录是否包含当日命名的完整资源集合。
- 检查 `wechat_article.md` 的图片引用是否全部可解析。
- 检查 HTML 内是否存在 `output/wechat_assets/` 这类旧路径。
- 检查 `output/` 中对应入口是否仍然指向最新文章目录。
- 检查最终读者版的内容是否只保留给公众号读者可见的信息，不包含内部制作说明。
- 检查正文是否先给事实、再给判断，而不是反过来。
- 检查全文高频套话是否已经被压到最低，尤其是 `不是……而是……` 句式。
- 检查任一段落删除形容词后是否仍然成立；若删完只剩空架子，需要补事实。

## 约束原则

- 公众号文章以“读者最终看到的内容”为准，不以内部制作过程为正文。
- 图片宁可少而整洁，也不要为了数量破坏排版。
- 复杂长图优先做总览板，必要时拆分为独立分享图区。
- 只有在用户确认最终读者版后，才同步公众号草稿箱。
- 先保证可读，再追求完整；先保证像人写的，再追求“总结得漂亮”。
